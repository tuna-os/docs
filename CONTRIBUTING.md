# Contributing

Thanks for your interest! This project is part of the [TunaOS](https://tunaos.org) ecosystem.

## Getting Started

### Local Environment Setup

**Prerequisites:**
- Node.js 24 or later (check with `node --version`)
- npm 10+ (check with `npm --version`)
- [just](https://github.com/casey/just) command runner (check with `just --version`)

**First-time setup:**

```bash
# Fork the repository on GitHub (button in the top right)
git clone https://github.com/<your-username>/docs.git
cd docs
npm ci                  # Clean install with exact pinned versions
just setup              # Verify all tools and print versions
```

**Local development:**

```bash
just start              # Start dev server (http://localhost:3000, hot-reload)
```

Open a browser to `http://localhost:3000` and make edits — the site reloads automatically.

**Before submitting a PR:**

```bash
just build              # Production build to `build/` directory
just preflight          # Type-check, lint, validate links, run tests
```

If `just preflight` fails, run `just fix` to auto-format and try again.

### Opening an Issue

Open an issue before a substantial documentation or site change (new sections,
navigation rework, new components) so maintainers can confirm its scope.
Small fixes (typos, links, single-page updates) do not need pre-approval.

## Content Model: Hand-Written vs. Synced

Understanding which docs are permanent and which are auto-generated prevents duplicated work.

### Hand-Written Content (Persistent)

**Location:** Top-level `docs/`, `blog/`, and `src/`  
**Persistence:** Edits are permanent. Your changes stay in place after merge.  
**Ownership:** Maintained here in tuna-os/docs.  
**Examples:**
- `docs/USER-GUIDE.md` — user-facing guides
- `docs/architecture.md` — architecture docs
- `blog/YYYY-MM-DD-slug.md` — blog posts
- Navigation config in `docusaurus.config.js`

**Edit these directly.** Open a PR when ready.

### Synced Content (Auto-Generated, Transient)

**Location:** `docs/<project>/` subdirectories (e.g., `docs/tunaos/`, `docs/bootc-installer/`)  
**Persistence:** Overwritten daily by [`sync-org-docs.yml`](/.github/workflows/sync-org-docs.yml).  
**Source:** Each `<project>` directory mirrors a repository in the tuna-os org.  
**SLA:** Sync runs daily at 6 AM UTC. Edits to synced pages are lost within 24 hours.  
**Ownership:** Original repository (e.g., fixes to `docs/tunaos/ROADMAP.md` are owned by tuna-os/tunaos).  
**Examples:**
- `docs/tunaos/README.md` synced from tuna-os/tunaos `README.md`
- `docs/bootc-installer/CONTRIBUTING.md` synced from tuna-os/bootc-installer `CONTRIBUTING.md`
- `docs/docs/ROADMAP.md` synced from tuna-os/docs `ROADMAP.md`

**To fix synced content:**

1. **Edit the source repository**, not the sync destination.
2. Example: To fix `docs/tunaos/README.md`, edit `README.md` in [tuna-os/tunaos](https://github.com/tuna-os/tunaos).
3. **Wait for the next sync** — the fix appears here within 24 hours (usually sooner).

**Finding the source:**

Each synced directory opens with a front-matter comment naming its source repo:

```markdown
<!-- Generated by sync-org-docs from tuna-os/tunaos — do not edit directly -->
```

**Boundaries & Exceptions:**

Some projects have both hand-written and synced pages. For example:
- `docs/tunaos/` is synced from tuna-os/tunaos
- But `docs/tunaos-variants/` is hand-written here (conceptual, not source-mirrored)

Check the front-matter comment to be sure.

**For more details:** See the generated-content section of [`AGENTS.md`](./AGENTS.md).

## Validation

Install the Markdown linter used by the repository recipe:

```bash
npm install --global markdownlint-cli
```

Run all local pre-submission checks:

```bash
just preflight
```

This command type-checks the site, checks Markdown and JavaScript, enforces the
prose budget for Simplified Technical English, and runs tests for documentation
scripts. Also run `just build` when the change can affect the generated site.

Use `just --list` to see individual setup, preview, build, and validation
recipes.

## Synchronized Project Documentation

The daily sync of documentation generates many `docs/<project>/` trees from
their source repositories. Fix documentation for a generated project in its
source repository. The next sync overwrites direct changes here. The generated
index page at the start of a project tree identifies the source repository.

## Pull Requests

- Keep PRs focused — one change per PR.
- Include the commands you ran in the PR description.
- Do not commit `build/`, dependency directories, or local preview output.
- Update navigation and cross-references when you add, move, or remove a page.

## Blog Posts

- Blog posts live in `blog/` with a `YYYY-MM-DD-<slug>.md` filename.
- Each post's `slug:` must be unique across `blog/`.
- A duplicate slug shadows the other post at the same URL and breaks canonical links.
- If you rewrite a post, reuse the existing file (update it in place).
- Do not add a second file with the same slug.
- **Publish before you merge.** A post is visible on tunaos.org/blog only when it has no `draft: true` in its frontmatter. Merge posts with `draft: false` (or no draft field) unless you schedule them for a future date (for example, 08-22). If you leave `draft: true` after the merge, the post stays hidden — flip the flag in the same PR.
- After you edit a post, run `just preflight` and `just build`. These checks
  include blog content in the prose budget and production build.
