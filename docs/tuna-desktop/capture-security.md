ScreenCast session creation and Screenshot requests require the supervised shell or the installed GNOME portal backend. The shell is recognised only by the session-bus unique names it declared over its `SO_PEERPIDFD`-pinned control session (`DeclareBusName`, protocol 0.52); the bus never reuses a unique name, so neither PID reuse nor a bus without `ProcessFD` can make another connection the shell. Portal admission checks ownership of `org.freedesktop.impl.portal.desktop.gnome` and that `/proc/PID/exe` identifies the root-owned, non-group/world-writable installed `/usr/libexec/xdg-desktop-portal-gnome` or `/usr/lib/xdg-desktop-portal-gnome` executable. Where the bus supplies `ProcessFD` (dbus-broker, dbus-daemon 1.15.8 and later), that PID is read through the pidfd: the descriptor must name the reported PID and its process must still be alive after `/proc/PID/exe` was read. An older bus leaves the numeric PID. Claiming a well-known name alone does not grant capture. There is no capture test environment bypass. Window introspection shares the same admission and locked-session gate; its existing explicit unrestricted debug setting only permits metadata while unlocked.

The portal is the trusted consent broker; this check authenticates the broker, rather than implementing its picker. Applications must use the external desktop portal. The supervised shell's screenshot UI supplies explicit local selection and Capture actions. The shell's public recorder D-Bus methods deny external calls, so an arbitrary caller cannot borrow the shell's trusted compositor connection.

Each ScreenCast session belongs to its unique creator. Only that creator may add streams, start or stop it. Start is single-use for the session and for each stream; as in Mutter, a stream added after Start waits for its own `Stream.Start`. Revocation is permanent. Registries admit at most 256 sessions and 64 streams per session. The compositor denies queued starts when locked or already revoked; lock closes all active PipeWire streams in its next tick, and existing offscreen capture paths also refuse locked frames. Idle dimming or blanking before lock does not itself revoke a grant.

The D-Bus service scans grants every 100 ms. Losing the creator connection, the trusted portal name, the supervised shell's declaration of the creator's unique name (a shell restart, or its control session ending) or unlocked state revokes the grant and queues stream teardown. The normal disconnect teardown latency is the scan interval plus one compositor tick; this is not a hard real-time guarantee under CPU starvation. Explicit Stop revokes immediately before queuing teardown. Closed session/stream objects are removed from the bus and registry.

The packaged `portal-security` lane uses the installed GNOME 51 backend and portal frontend with the CI-built compositor and GTK shell. It records package versions and the exact candidate merge commit. Applications exercise real Cancel/Share consent, OpenPipeWireRemote and a decoded frame. Foreign owners, ordinary unknown callers and a forged portal name are denied. Owner Close, frontend/backend disconnect and lock remove the PipeWire node; the accepted journey requires removal within two seconds. The Ubuntu GTK lane additionally proves UI Stop and active recording revocation on lock, with unchanged accessibility goldens.

Remote Desktop shares this authenticated authority and binds keyboard/pointer and linked ScreenCast grants to their original caller. RemoteDesktop.CreateSession, and only the ScreenCast session linked to that grant, additionally admit the installed root-owned gnome-remote-desktop daemon by executable identity, grd bus name and enabled Desktop Sharing GSettings (Tuna Desktop hardening; Mutter 51 has no such gate); it gets no other capture API. Its independent installed libei client must deliver real GTK key/button events, then prove node withdrawal, no further input and an empty held seat on revocation. See [Remote Desktop](https://github.com/tuna-os/tuna-desktop/blob/main/docs/remote-desktop.md) for bounds and unsupported capabilities.

No grant is silent (#1162 F2). The compositor publishes mutter 51's remote access handles to the shell over the control socket (wire 0.54 `RemoteAccess`): every started ScreenCast session (plain or linked), every started RemoteDesktop session and every InputCapture session while it captures, each with its kind, id, targets (monitor, window, area or input), owner (shell, portal or grd, with its unique bus name) and whether all its streams were recorded with `is-recording`. The scan publishes a change within its 100 ms period. The shell shows GNOME 51's indicators from `js/ui/status/remoteAccess.js`: the orange `ScreenSharingIndicator` panel button ("Stop Screen Sharing") while any non-recording grant is active, shown at least five seconds, and the orange `media-record-symbolic` privacy icon for a recording grant. The shell's own recorder is a recording grant owned by the shell and keeps only its red "Stop Screencast" button, as GNOME leaves the screenshot UI's screencast out. GNOME 51 adds no quick settings item for either; the panel button is the Stop. Pressing it sends `StopRemoteAccess` for each grant it shows; the compositor accepts only a published grant and the scan revokes it permanently at once, as `meta_remote_access_handle_stop` closes its session: the stream and the PipeWire node go, the owner is told (`Closed`) and its every later call is denied. Stopping a linked ScreenCast ends its RemoteDesktop grant too. Lock still revokes every grant as before. `G-REMOTE-ACCESS-INDICATOR` (`scripts/tuna-gtk-shell-proof --remote-access-only`, and the full proof after `G-PORTAL-CONSENT`) grants a real portal share, finds the button through AT-SPI, presses it, requires node withdrawal within two seconds and the app's portal session `Closed`, then requires the button gone.

Screenshot uses the installed GTK backend only for its Access consent UI. Deny returns no URI; Allow must yield a readable image. An authenticated locked request returns the documented false/empty result without scheduling capture, and the proof requires an empty frontend URI and unchanged saved-image hashes. Unknown callers retain AccessDenied. See [Screenshot consent](https://github.com/tuna-os/tuna-desktop/blob/main/docs/portal-screenshot-consent.md).

The [dated qualification manifest](https://github.com/tuna-os/tuna-desktop/blob/main/docs/capture-evidence.json) records actual current-head runs, candidate parents, runtime versions and retained artifacts. Issue #61's consent, real-stream, bounded-revocation and locked-denial acceptance is separate from full GNOME parity: touch, text input, interactive portal screenshot customization, area/color selection, cursor metadata and dmabuf zero-copy remain explicit limitations (keysyms and the session clipboard are implemented for #358). P-SY-05 therefore remains partial.
